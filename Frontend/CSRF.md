### Cross-Site Request Forgery (CSRF)

Cross-Site Request Forgery (CSRF) is a web security vulnerability that forces an end user's web browser to execute an unauthorized HTTP request against a web application where the user is currently authenticated.

### The Core Mechanism

CSRF exploits a specific, default behavior of web browsers: the automatic inclusion of ambient credentials.

When a browser makes an HTTP request to a specific domain, it automatically attaches any existing, valid cookies associated with that domain. This automatic attachment occurs regardless of where the request originally originated.

A successful CSRF execution requires three specific conditions to be met simultaneously:

1. **Active Authentication:** The user must have an active session with a target application (e.g., an established session cookie stored in the browser).
2. **Predictable Endpoint:** The target application must contain a state-changing operation (such as modifying an account or deleting a record) accessible via a predictable HTTP request format.
3. **Implicit Trust:** The target application relies strictly on the automatically submitted session cookie to verify the identity of the user, without requiring any secondary, request-specific validation.

### Execution Sequence

1. The user logs into a legitimate application, and the server establishes a session, storing a session cookie in the user's browser.
2. Without logging out, the user navigates to a different, third-party webpage controlled by an attacker.
3. The malicious webpage contains code (such as an automatically submitting HTML form or a background script) configured to send an HTTP POST request to the legitimate application's predictable endpoint.
4. The user's browser executes the request. Because the request is addressed to the legitimate application, the browser automatically attaches the user's active session cookie.
5. The legitimate application receives the request, validates the session cookie, and executes the state-changing operation, processing the request as if the user explicitly initiated it.

### Standard Defense Mechanisms

To prevent CSRF, an application must require proof that the HTTP request was intentionally generated by its own client interface, not a third-party site.

#### Anti-CSRF Tokens (Synchronizer Token Pattern)

This is the traditional defense strategy.

* The server generates a cryptographically random, unpredictable string (the token) and sends it to the client.
* When the client submits a state-changing request, it must explicitly include this token in a hidden form field or a custom HTTP header.
* The server immediately rejects any request that lacks the correct token.
* Because the Same-Origin Policy (SOP) prevents the malicious webpage from reading the legitimate application's DOM or HTTP responses, the attacker cannot read or extract the required token, causing the forged request to fail validation.

#### The SameSite Cookie Attribute

This is a browser-level defense mechanism configured via the `Set-Cookie` HTTP response header. It explicitly dictates when the browser is permitted to send a cookie in a cross-origin context.

* **Strict:** Instructs the browser to strictly withhold the cookie from any request initiated by a different domain.
* **Lax:** Instructs the browser to withhold the cookie for cross-domain POST requests (which are typically used for destructive state changes) but permits it for safe, top-level navigation GET requests.
By enforcing `SameSite=Lax` or `Strict`, the application ensures the browser will not automatically append the session cookie when the malicious site attempts to trigger the forged request.

#### Custom HTTP Headers

Modern Single Page Applications (SPAs) frequently mitigate CSRF by requiring custom HTTP headers (e.g., `X-Requested-With: XMLHttpRequest`) on all state-changing requests.

* Due to Cross-Origin Resource Sharing (CORS) security protocols, a browser will not permit a third-party site to append custom headers to a cross-origin request without first successfully completing an HTTP `OPTIONS` preflight request.
* If the legitimate server is properly configured to reject CORS preflight requests from unauthorized origins, the browser will strictly block the malicious script from sending the actual POST request containing the custom header.
